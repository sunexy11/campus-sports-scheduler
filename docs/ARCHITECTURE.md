# 系统架构

## 运行职责划分

- Cron-job.org 每天 06:50 通过 GitHub `workflow_dispatch` 触发定时预约 Workflow；Workflow 准备
  环境并登录后等待到 07:00，再提交预约。
- GitHub Actions 中的 Node/JSDOM 桥负责执行预约站点的瑞数校验；Python 和桥在同一个任务内保持预约会话。
- Cloudflare Workers 暂不承担预约系统请求：当前接口的瑞数校验需要 Node/JSDOM 的运行环境，Workers 不能直接复用这套会话。
- Cron-job.org 在 07:00–23:55 每 5 分钟触发一次 `monitor-once`；公开仓库使用标准 Runner 不消耗
  私有仓库的分钟额度，但仍需防止监控任务重叠和 GitHub Runner 排队。
- QQ SMTP 是唯一的通知渠道。

## 核心安全约束

1. 未结束预约总数永远不得超过三个。
2. 每次提交预约前都必须重新查询未结束预约数量。
3. 达到三个预约后继续监控和提醒，但不得继续预约。
4. 永远不自动取消预约；实际预约接口中也不会提供取消方法。
5. 如果提交请求超时，必须先查询预约列表，确认是否已经成功，再决定能否重试。
6. 遇到限流或访问被拒绝时立即停止，不进行高频重试。
7. 配置和策略不要求用户指定具体子场地；程序只把接口返回的可用子场地作为一次性提交候选。

## 日历查询接口

网页预约日历使用 `/reservation/site/resource/calendar`，通过
`date={start_date,end_date}` 的 JSON 参数查询日期范围。响应按“日期 → 子场地 → 时段”
返回状态：`status=0` 为可预约，`status=2` 为已过期，`status=3` 为约满，另有未开放和禁用状态。
程序直接采用站点返回的状态，不再用本地当前时间推断某个时段是否已过期；旧的
`/api/resource/large-screen` 仅保留为兼容性探测接口，不参与空位监控。

## 日期和时段如何识别

程序不会从网页 URL 推断日期。每次查询都会调用网页实际使用的
`/reservation/site/resource/calendar` 接口，并把目标日期放在
`date={"start_date":"YYYY-MM-DD","end_date":"YYYY-MM-DD"}` 参数中。
接口返回的 `data` 第一层是明确的日期，第二层是子场地 ID，第三层是时段 ID；
`time` 数组把时段 ID 映射为显示文本，例如 `3899 → 12:00-13:00`。
因此程序只读取目标日期这一层，再按 `status=0` 且 `num>0` 判断可预约，并保留该
时段对应的可用子场地 ID。`status=2`（已过期）和 `status=3`（已满）不会报告，
也不会自行用本地时钟覆盖网站状态。

监控任务的 `dates` 支持三种写法：`next_3_days`（兼容旧配置，表示今天、明天、后天）、
偏移量列表（例如 `[0, 1, 2]`、`[1, 2]` 或 `[]`，分别表示从运行当天起的相对日期），
以及明确的 `YYYY-MM-DD` 日期列表。偏移量只能是 `0`、`1`、`2`；空列表表示本次任务不查询
任何日期。列表中的重复日期会被去重，但保留第一次出现的顺序。

`monitor.jobs` 是任务列表，不是只能配置一个任务。每个任务可以独立设置“场馆 + 球类”、
日期、时间段、提醒/自动预约模式和 `max_new_reservations`；一次运行会依次扫描所有任务，
并把结果合并到同一份输出和通知中。

## 预约策略

- 配置单位是“场馆 + 球类”，例如“北区体育馆 + 羽毛球”。
- 按配置中的场馆顺序和时间组合顺序，从高优先级到低优先级尝试。
- 优先预约完整的连续时段；允许时，再降级为单个时段。
- 每轮最多预约 `3 - 当前未结束预约数` 个，同时还受任务自身的预约上限约束；多个监控任务和
  多个定时任务共享同一个全局上限，不会各自把上限计算一遍。
- 已有预约不会因为出现更高优先级空位而被取消或替换。

## 预约提交和竞争处理

- `monitor-once` 默认只查询；只有显式传入 `--allow-booking`，且监控任务的
  `mode` 为 `auto_book_if_capacity` 时才会提交预约。
- `scheduled-book-once` 默认是演练模式；传入 `--allow-booking` 才会按照连续时段、
  场馆和时间优先级尝试预约。
- 每一次提交前都会重新读取未结束预约数，达到 3 个立即停止提交，不会取消已有预约。
- 代码同时累计本次运行已经成功的提交，即使服务端的预约列表暂时尚未刷新，也不会在同一次
  运行中突破全局上限。
- 日历读到空位后，如果提交时已被其他人抢走，接口会返回非致命结果
  `slot_unavailable`；程序记录这次尝试，继续尝试其他候选，并重新扫描有限轮次。
  这类竞争不会让 GitHub Actions 失败，也不会阻断后续监控任务。
- 如果接口返回“预约时间不可重叠”或同义提示，结果会标记为
  `overlap_with_existing`，只跳过该候选，继续尝试其他日期或时间段；这同样不会让任务失败。
- 如果预约提交接口返回 HTTP 412，Node/JSDOM 桥会先对同域挑战 HTML 最多等待 1 秒并重试原请求。
  如果第二次提交仍为 412，再执行一轮最多等待 5 秒的挑战并进行最后一次提交。只有最后仍为 412
  时，程序才会报告预约验证/瑞数校验问题；这不是空位竞争，不能安全地吞掉。等待时间可分别由
  `FUDAN_POST_CHALLENGE_TIMEOUT_MS` 和 `FUDAN_POST_RETRY_CHALLENGE_TIMEOUT_MS` 覆盖。
- 预约接口使用当前网页的 sports payload：提交父场馆 ID、当前仍可用的子场地 ID 集合、
  时段 ID 和日期，由站点在集合中分配，不会调用取消接口。子场地集合只是提交瞬间的候选，
  不会变成用户配置中的固定场地。

## 分阶段上线

1. 完成离线策略测试和配置校验。
2. 只读验证 UIS 登录和预约系统登录。普通账号仅使用用户名、密码；只有 UIS 明确要求二次认证时才使用可选的 TOTP。
3. 只读查询场馆、空闲时段和未结束预约数量。
4. 在 GitHub Actions 或其他可运行 Node 24 的环境中验证会话复用；Cloudflare Worker 暂不纳入主链路。
5. 对用户指定的目标执行一次不提交的演练（`scheduled-book-once` 不带开关）。
6. 经用户确认后手动运行一次带 `--allow-booking` 的真实预约。
7. 当前示例已经将目标定时任务设置为 `scheduled_jobs[].enabled: true`；如果只想干跑，先改回
   `false`，或使用手动 Actions 并保持 `allow_booking: false`。
8. “仅提醒”监控稳定后，再将监控任务设置为 `auto_book_if_capacity`，并在 Cron-job.org 请求体中
   将 `allow_booking` 改为 `true`。
