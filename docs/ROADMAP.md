## 第一阶段：真实只读联调

目标是确认登录协议、场馆编号、日程响应格式和预约数量统计，绝不提交预约。

需要用户介入：

1. 在自己的终端中运行 `fudan-booking probe --prompt-credentials`。
2. 不要在聊天或截图中暴露密码、Cookie、TOTP 种子。
3. 把命令输出的场馆列表和未结束预约数量反馈回来；这些输出已经去除认证信息。
4. 选择一个场馆编号和三天内的日期，再执行一次指定日程探测。

需要用户仲裁：如果 UIS 实际要求的二次认证不是 TOTP，需由用户决定是否停止自动登录方案。项目不会尝试绕过短信、扫码、设备确认或验证码。

### 已解决的联调问题：HTTP 412

UIS 的用户名密码认证已经能够走到 CAS 票据生成；但最终访问
`booking.fudan.edu.cn/reservation/api/login/cas` 时，服务端返回 HTTP 412，响应是瑞数
JavaScript 反爬挑战页。`ehall` 的原始纯 `requests` 实现和本项目当前实现都会在同一步失败，
所以这不是账号密码或 `.env` 格式问题。

用户已同意第二种方案。当前桥不启动浏览器，认证票据只通过标准输入传递给本机 Node 进程，
普通查询只允许场馆列表、日程、预约列表，以及网页预约表单所需的资源详情和账号联系方式 GET 接口；
预约提交仅开放固定的体育场馆端点。
真实账号联调已经能够返回场馆列表、日程空位和未结束预约数量；预约提交默认关闭，需显式开关。
预约列表、场馆列表、日历等只读 GET 和预约 POST 遇到同域瑞数 412 时，都会在 Node/JSDOM 桥中执行挑战，
并同时监听页面完成事件和 Cookie 更新；
任一信号出现就提前重试一次。两轮默认各最多 8 秒，若 Cookie 提前更新则立即继续；若重试仍为 412，
再执行第二轮挑战并最后提交。
最终仍为 412 时会报告两轮挑战的耗时和完成信号；真实账号已验证提交成功。

## 第二阶段：只读监控与通知

目标是先在能保持 Node 会话的运行环境中查询，并在发现指定场馆和时间有空位时发送 QQ 邮件。

实施内容：

1. 把日程响应转换成统一的“场馆 + 球类 + 日期 + 时间 + 是否可约”数据。
2. 保存上一次空位状态，只有从“无空位”变为“有空位”时通知，避免每五分钟重复发信。
3. 实现认证失效、限流、接口异常等单独告警。
4. 验证 GitHub Actions 通过 TLS 465 端口连接 QQ SMTP。

需要用户介入：在 QQ 邮箱中开启 SMTP 并生成授权码；接收一封测试邮件并确认结果。

需要用户仲裁：5 分钟全天监控会超过 GitHub Actions 私有仓库免费额度；届时需要在降低频率和选择其他免费运行环境之间决定。

## 第三阶段：预约能力

目标是在不超过三个未结束预约的前提下，按优先级预约；永远不取消已有预约。

每次提交前按以下顺序执行：

1. 重新登录或确认会话有效。
2. 重新统计未结束预约数量。
3. 如果数量已达三个，只提醒，不提交。
4. 重新查询目标时段，避免使用过期的空位结果。
5. 按完整连续时段优先、场馆和时间优先级依次尝试。
6. 提交请求后查询预约列表确认结果；超时不能直接重复提交。

需要用户介入：先确认演练输出中的预约目标，再确认默认预约人数和首次目标组合；手机号沿用预约系统账号侧的默认填写值。

需要用户仲裁：首次真实预约前，用户必须确认具体的“场馆 + 球类 + 日期 + 时间组合”和最多新预约数量。首次成功后再决定是否允许自动定时运行。

## 第四阶段：正式调度

定时预约计划：

- 06:50：GitHub Actions 启动，安装依赖并进行配置检查。
- 环境准备完成后：登录并读取最新场馆、预约数量和目标日程。
- 07:00：重新检查容量和空位后提交。

监控计划：

- 每天 07:00 至 23:55，每五分钟一次。
- 达到三个未结束预约后跳过本次监控和预约，不取消已有预约。
- 发现指定空位时，可以在容量允许的情况下自动预约。

需要用户介入：在 GitHub 仓库中配置 Secrets，并手动启用两个定时器。仓库可以公开，但不得
提交任何个人凭据或登录材料。

需要用户仲裁：正式启用前确认最终配置；以后若修改预约上限、时间范围、场馆优先级、通知渠道或自动预约范围，也必须由用户明确确认。
